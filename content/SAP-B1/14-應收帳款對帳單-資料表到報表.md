# 應收帳款對帳單：從資料表到報表的完整路徑

## 前言

應收帳款對帳單（AR Statement）是每位 SAP B1 顧問遲早都會接到的報表需求。客戶每個月底要寄給往來廠商的對帳單，列明期間內的每筆應收款項，包含發票、銷貨退回、收款記錄，以及期末未銷帳款餘額。

這份報表看起來不難，但實際設計時會遇到幾個挑戰：應收交易分散在多張資料表、銷貨退回的金額符號需要反轉、已調節與未調節項目的判斷邏輯、以及如何讓合計行與明細行在同一份報表中呈現。本文以真實專案經驗為基礎，拆解從資料表理解到報表完成的完整路徑。

---

## 業務用途

在討論技術細節之前，先確認對帳單的業務意義：

- **客戶端用途**：核對當期出貨與付款記錄，確認雙方帳目一致
- **財務端用途**：確認應收帳款餘額，作為催收依據
- **稽核用途**：文件化每筆交易的來源單據，供對帳與爭議處理使用

對帳單通常「按客戶、按期間」產出，有時需要依集團（FatherCard）彙總，而非單一客戶代碼。這個業務需求會直接影響 SQL 的 GROUP BY 設計。

---

## B1 應收相關資料表結構

理解資料表是設計 SQL 的前提。以下是應收模組最核心的幾張資料表：

### 主表（Document Header）

| 資料表 | 說明 | 關鍵欄位 |
|--------|------|----------|
| OINV | 應收發票（AR Invoice） | DocEntry, DocNum, CardCode, DocDate, DocDueDate, DocTotal, PaidToDate |
| ORIN | 應收貸項通知單（AR Credit Note，即銷貨退回） | DocEntry, DocNum, CardCode, DocDate, DocTotal, PaidToDate |

### 明細表（Document Lines）

| 資料表 | 說明 | 與主表的關聯 |
|--------|------|-------------|
| INV1 | OINV 的明細行 | INV1.DocEntry = OINV.DocEntry |
| RIN1 | ORIN 的明細行 | RIN1.DocEntry = ORIN.DocEntry |

### 付款與調節

| 資料表 | 說明 |
|--------|------|
| ORCT | 應收款項（Incoming Payments） |
| OJDT / JDT1 | 日記帳分錄，用於查詢已調節項目 |
| OITR / ITR1 | 內部調節（Internal Reconciliation）記錄 |

### 重要欄位說明

- `DocTotal`：文件總金額（含稅）
- `PaidToDate`：至今已付金額（B1 動態計算）
- `DocTotal - PaidToDate`：**未銷帳款（Open Amount）**，這是對帳單最核心的數字
- `DocStatus`：文件狀態，`'O'` 表示未關閉（Open），對帳單通常只列 Open 的文件

另外需注意 OINV 與 ORIN 的日期欄位差異：
- OINV：`DocDate`（過帳日）與 `DocDueDate`（到期日）可以不同
- ORIN：理論上兩者應相同，若不同通常代表是已取消的文件，查詢時需加 `WHERE CANCELED = 'N'`

## 對帳單 SQL 設計思路

### 為什麼需要 UNION

應收模組的交易分散在多張資料表，單一 SELECT 無法同時取出發票與銷貨退回。設計對帳單 SQL 的核心思路是：**用 UNION ALL 將不同交易類型的資料「垂直合併」成同一個結果集**，再由報表層做分組與排序。

基本結構如下：

```sql
-- 段落 1：應收發票（OINV）
SELECT 
    '1'            AS SortKey,
    OINV.CardCode,
    OCRD.CardName,
    OINV.DocNum,
    OINV.DocDate,
    'AR'           AS DocType,
    (OINV.DocTotal - OINV.PaidToDate) AS OpenAmt
FROM OINV
JOIN OCRD ON OINV.CardCode = OCRD.CardCode
WHERE OINV.CardCode BETWEEN '{?CARDFROM}' AND '{?CARDTO}'
  AND OINV.DocDate BETWEEN {?DAYFROM} AND {?DAYTO}
  AND OINV.DocStatus = 'O'
  AND OINV.CANCELED = 'N'

UNION ALL

-- 段落 2：銷貨退回（ORIN），金額需乘以 -1
SELECT 
    '2'            AS SortKey,
    ORIN.CardCode,
    OCRD.CardName,
    ORIN.DocNum,
    ORIN.DocDate,
    'CN'           AS DocType,
    (ORIN.DocTotal - ORIN.PaidToDate) * -1 AS OpenAmt
FROM ORIN
JOIN OCRD ON ORIN.CardCode = OCRD.CardCode
WHERE ORIN.CardCode BETWEEN '{?CARDFROM}' AND '{?CARDTO}'
  AND ORIN.DocDate BETWEEN {?DAYFROM} AND {?DAYTO}
  AND ORIN.DocStatus = 'O'
  AND ORIN.CANCELED = 'N'

ORDER BY CardCode, SortKey, DocDate, DocNum
```

**關鍵設計決策：銷貨退回金額乘以 -1**

ORIN 的 `DocTotal` 在資料庫中是正數，但在對帳單上代表「扣減」。若不加 `* -1`，對帳單的合計數字會算錯。這是初次設計應收對帳單最容易犯的邏輯錯誤。

## 實務案例：多業別對帳單（UNION 多段）

在真實專案中，同一家客戶可能有多種業務類型（例如手錶產品線、零件、維修服務），每種業務類型需要分開統計小計，最後再合計。這時候 SQL 結構會擴展成多段 UNION，並加入小計行：

```sql
-- 業別 1：CB（Citizen Watch）發票
SELECT '1' AS SortKey, OINV.CardCode, ... 
FROM OINV ...
WHERE ... AND OINV.U_AcctGrp = 'Citizen Watch'

UNION ALL

-- 業別 2：MB（Multi Brand Watch）發票  
SELECT '2' AS SortKey, OINV.CardCode, ...
FROM OINV ...
WHERE ... AND OINV.U_AcctGrp = 'Multi Brand Watch'

UNION ALL

-- 業別 3：銷貨退回（CB）
SELECT '3' AS SortKey, ORIN.CardCode, ...
    (ORIN.DocTotal - ORIN.PaidToDate) * -1 AS OpenAmt
FROM ORIN ...
WHERE ... AND ORIN.Series = '79'  -- 79 = CB 銷退

UNION ALL

-- 業別 4：銷貨退回（MB）
...
```

這種設計的 `SortKey`（排序碼）非常重要，它決定了報表中各類型明細的顯示順序，在 CR 報表的 Group 設定中以此欄位控制分頁與小計位置。

## 進階：加入已調節項目（JDT1）

有些客戶需要在對帳單中同時顯示「已調節（已核銷）」的日記帳分錄，例如存款退款或沖帳。這時需要加入 JDT1（日記帳明細）的資料：

```sql
-- 已調節的日記帳分錄
SELECT '5' AS SortKey,
    T0.ShortName  AS CardCode,
    T0.Account,
    SUM(T0.Debit - T0.Credit) AS OpenAmt,
    '已調節' AS DocType
FROM JDT1 T0
WHERE T0.Account = '11101'           -- 應收帳款科目
  AND T0.IntrnMatch > 0              -- 有調節記錄
  AND T0.MthDate BETWEEN [%0] AND CONVERT(date, GETDATE())
GROUP BY T0.IntrnMatch, T0.ShortName, T0.Account
HAVING SUM(T0.Debit - T0.Credit) <> 0
```

這段 SQL 的設計邏輯：透過 `IntrnMatch` 欄位識別已調節的交易（值 > 0 表示有對應的調節記錄），再用 `MthDate`（調節日期）作為時間篩選。需注意 B1 的內建 Query 不支援 CTE（WITH 語句），所以這類複雜邏輯通常需要使用暫存資料表（Temp Table）。

## 格式要求

對帳單的格式通常有以下幾個業務要求：

1. **每個客戶獨立一頁**：CR 中使用「依 CardCode 分組」並設定「每組後換頁」
2. **小計與總計**：在 Group Footer 放置加總公式，在 Report Footer 放置總計
3. **發票號碼與統一發票號並列**：部分台灣客戶需要同時顯示 B1 單號（DocNum）與政府規定的統一發票號（`U_INV_InvoiceNum`）
4. **貨幣符號與小數位數**：金額欄位統一格式，避免因資料為空時顯示異常
5. **列印日期**：在 Page Footer 加入 `Now()` 函數，自動帶出列印日期

## 與其他報表的配合

應收帳款對帳單通常不是孤立的報表，它會和以下流程搭配使用：

- **應收帳款明細表**（如 F12）：對帳單給客戶看，明細表是財務內部核對用，兩者的未銷帳款合計數應一致，若不一致代表 SQL 邏輯有誤
- **收款記錄（ORCT）**：對帳單顯示未銷帳款，收款記錄確認付款日期，兩者互為補充
- **催收清單**：以對帳單資料為基礎，加上到期日判斷，產生逾期帳款清單

## 常見陷阱

- **忘記排除取消文件**：OINV 與 ORIN 都有 `CANCELED` 欄位，對帳單必須加 `AND CANCELED = 'N'`，否則已取消的發票也會出現在報表中
- **ORIN 金額未乘以 -1**：銷貨退回的 `DocTotal` 在資料庫是正數，但對帳單邏輯上是扣減，忘記取負值會導致合計數字偏高
- **PaidToDate 邏輯混淆**：`PaidToDate` 是動態計算的累計收款，不代表「當期」收款。若要計算特定期間的收款，應查詢 ORCT 或 JDT1，而非直接使用 `PaidToDate`
- **集團帳與個別帳**：若客戶要求以「集團（FatherCard）」為單位出對帳單，需確認 OCRD 的 `FatherCard` 欄位有正確設定，並調整 SQL 的 GROUP BY 邏輯

## 顧問建議

應收帳款對帳單是一個很好的學習載體，因為它綜合了 B1 資料表關係、SQL UNION 設計、CR 分組格式化，以及業務邏輯理解等多個面向。

建議的學習路徑：先在 SSMS（SQL Server Management Studio）裡把 SQL 跑通，確認每個 UNION 段落的資料正確；再把驗證過的 SQL 貼入 CR 的 Command 物件；最後才開始處理報表格式。這樣的順序可以讓你在最短的時間內隔離問題，不會把「資料問題」和「格式問題」混在一起除錯。

另外，每次設計對帳單類報表，都建議先和客戶財務確認「未銷帳款的定義」—有些客戶的「對帳」是以到期日為準，有些是以過帳日為準，有些要包含草稿狀態的文件。這些細節若在需求確認階段沒有釐清，後期改動的成本會很高。
