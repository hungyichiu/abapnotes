# 如何設計核准範本

## 問題背景

客戶的組織一直在變。主管升遷、離職、部門重組，核決設定卻很少跟著更新。等到某張採購單卡在「待核決」超過一週，才發現原來負責核決的人早就不在了。

這時候你需要做的第一件事，是快速盤點：**系統裡現在有哪些核決範本、每個階段是誰在負責**。靠著一頁一頁翻設定畫面，效率極差。用 SQL 直接查，三分鐘搞定。

---

## 核決制度的兩個核心概念

B1 的核決制度由兩個層次組成：

| 物件 | Table | 說明 |
|------|-------|------|
| **核決階段（Approval Stage）** | `OWST` / `WST1` | 定義「誰」負責核決，以及幾票同意才算通過 |
| **核決範本（Approval Template）** | `WTM1` / `WTM2` | 定義「什麼條件」下觸發核決，以及階段的執行順序 |

設定路徑：
> [!info]
> 管理 → 核決程序 → 核決階段
> 管理 → 核決程序 → 核決範本

**核決階段**可以被多個核決範本共用，組織異動時只需要修改核決階段裡的人員，就能同時更新所有引用它的範本。

---

## 相關資料表

| Table | 說明 |
|-------|------|
| `OWST` | 核決階段主檔（Stage Header） |
| `WST1` | 核決階段的核決人員清單 |
| `WTM1` | 核決範本主檔（Template Header） |
| `WTM2` | 核決範本包含的核決階段清單 |
| `OUSR` | 系統使用者主檔（對應 UserID 取得姓名） |

---

## SQL 查詢

### 1. 盤點所有核決階段與範本的對應關係

```sql
SELECT
    T0.WstCode        AS 核決階段代碼,
    T0.Name           AS 核決階段名稱,
    T0.MaxReqr        AS 最低通過票數,
    T0.MaxRejReqr     AS 最低駁回票數,
    T1.UserID         AS 核決人員ID,
    T3.WtmCode        AS 所屬範本代碼
FROM [dbo].[OWST] T0
INNER JOIN [dbo].[WST1] T2 ON T0.[WstCode] = T2.[WstCode]
INNER JOIN [dbo].[WTM2] T3 ON T0.[WstCode] = T3.[WstCode]
```

**用途**：一次看清楚所有核決階段的人員，以及這些階段被哪些範本引用。

---

### 2. 查詢指定人員負責哪些核決階段

```sql
SELECT
    T0.WstCode  AS 核決階段代碼,
    T0.UserID   AS 使用者ID,
    T1.U_NAME   AS 使用者姓名
FROM WST1 T0
INNER JOIN OUSR T1 ON T0.UserID = T1.USERID
WHERE T1.U_NAME = [%0]
```

**用途**：主管離職前，快速確認他負責哪些核決階段，以便交接或替換。執行時輸入姓名即可篩選。

---

### 3. 查詢指定人員建立了哪些核決範本

```sql
SELECT
    T0.WtmCode  AS 核決範本代碼,
    T0.UserID   AS 建立者ID,
    T1.U_NAME   AS 建立者姓名
FROM WTM1 T0
INNER JOIN OUSR T1 ON T0.UserID = T1.USERID
WHERE T1.U_NAME = [%0]
```

**用途**：追蹤範本的建立者，確認設定的脈絡。

## 常見情境與應對

### 情境一：核決卡住，不知道誰有權核決

執行查詢 1，找出卡住的單據對應的核決階段，確認目前的核決人員是誰，再聯絡對方處理。

### 情境二：主管異動，需要更新核決設定

執行查詢 2，輸入舊主管姓名，列出他負責的所有核決階段，逐一進入設定頁面替換核決人員。

### 情境三：系統整理，盤點所有現行核決架構

執行查詢 1，匯出結果給客戶的 IT 或管理部門確認，作為定期審查的依據。

---

## 常見陷阱

**陷阱一：修改核決階段後，舊的待核決單據不受影響**

已進入待核決狀態的單據，不會因為你更新了核決階段的人員就自動轉給新的核決者。需要手動重新提交，或請有權限的管理員強制通過。

**陷阱二：同一個人在多個階段出現**

一個使用者可能同時是多個核決階段的核決人，查詢 2 會把全部列出來，不要只改其中一個。

**陷阱三：核決範本的啟用條件未同步更新**

核決範本裡除了階段，還有觸發條件（如金額門檻、特定使用者）。更換核決人員時，順便確認觸發條件是否還符合現行制度。

---

## 實作提醒

- 每次客戶有人員異動，主動執行查詢 2 確認影響範圍，不要等單據卡住才處理
- 將查詢 1 的結果納入導入文件的「核決架構表」，定期更新
- 建議客戶建立「核決架構審查」的年度 SOP，由顧問或 IT 定期執行這幾支 SQL 並回報給管理層

## 相關：核決範本的觸發條件

核決範本除了定義「誰核決」，還需要定義「什麼條件下觸發」。B1 提供三種觸發條件：金額門檻、特定使用者，以及 User Query（本質是一段 SQL，回傳 `'TRUE'` 才觸發）。User Query 觸發條件的完整語法、依部門與金額分流的實戰案例、測試步驟，詳見 [[15-SAP B1 User Query|SAP B1 User Query]] 的「應用三：核決範本觸發條件」——兩篇分別聚焦「核決人員盤點」與「User Query 全方位應用」，避免重複維護同一段 SQL 案例。
