## 【So What】問題背景

客戶的組織一直在變。主管升遷、離職、部門重組，核准設定卻很少跟著更新。等到某張採購單卡在「待核准」超過一週，才發現原來負責核准的人早就不在了。

這時候你需要做的第一件事，是快速盤點：**系統裡現在有哪些核准範本、每個階段是誰在負責**。一頁一頁翻設定畫面很慢，用 SQL 直接查快得多。

這篇只講盤點。範本本身怎麼設定觸發條件，在 [[15-SAP B1 User Query|SAP B1 User Query]] 那篇。

---

## 【What】核准制度的兩個核心概念

B1 的核准制度由兩個層次組成：

| 物件 | Table | 說明 |
|------|-------|------|
| **核准階段（Approval Stage）** | `OWST` / `WST1` | 定義「誰」負責核准，以及幾票同意才算通過 |
| **核准範本（Approval Template）** | `OWTM` / `WTM1` / `WTM2` | 定義「誰送的單、什麼條件」會觸發核准，以及走哪些階段 |

設定路徑：
> [!info]
> 管理 → 核准程序 → 核准階段
> 管理 → 核准程序 → 核准範本

**核准階段**可以被多個核准範本共用，組織異動時只需要修改核准階段裡的人員，就能同時更新所有引用它的範本。

---

## 相關資料表

| Table | 說明 |
|-------|------|
| `OWST` | 核准階段主檔 |
| `WST1` | 核准階段的核准人員清單（`WstCode`、`UserID`） |
| `OWTM` | 核准範本主檔 |
| `WTM1` | 核准範本的發起人清單，也就是哪些使用者送單會套用這個範本（`WtmCode`、`UserID`） |
| `WTM2` | 核准範本包含的核准階段與順序（`WtmCode`、`WstCode`、`SortId`） |
| `OUSR` | 系統使用者主檔，用 `UserID` 對出姓名 |

下面三支查詢都在 MSSQL 的 B1 環境跑過。

---

## SQL 查詢

### 1. 盤點所有核准階段與範本的對應關係

```sql
SELECT
    T0.WstCode        AS 核准階段代碼,
    T0.Name           AS 核准階段名稱,
    T0.MaxReqr        AS 最低通過票數,
    T0.MaxRejReqr     AS 最低駁回票數,
    T1.UserID         AS 核准人員ID,
    T2.WtmCode        AS 所屬範本代碼,
    T2.SortId         AS 階段順序
FROM OWST T0
INNER JOIN WST1 T1 ON T0.WstCode = T1.WstCode
INNER JOIN WTM2 T2 ON T0.WstCode = T2.WstCode
ORDER BY T2.WtmCode, T2.SortId
```

**用途**：一次看清楚所有核准階段的人員，以及這些階段被哪些範本引用。

---

### 2. 查詢指定人員負責哪些核准階段

```sql
SELECT
    T0.WstCode  AS 核准階段代碼,
    T0.UserID   AS 使用者ID,
    T1.U_NAME   AS 使用者姓名
FROM WST1 T0
INNER JOIN OUSR T1 ON T0.UserID = T1.USERID
WHERE T1.U_NAME = [%0]
```

**用途**：主管離職前，快速確認他負責哪些核准階段，以便交接或替換。執行時輸入姓名即可篩選。

---

### 3. 查詢指定人員送單時會套用哪些核准範本

```sql
SELECT
    T0.WtmCode  AS 核准範本代碼,
    T0.UserID   AS 發起人ID,
    T1.U_NAME   AS 發起人姓名
FROM WTM1 T0
INNER JOIN OUSR T1 ON T0.UserID = T1.USERID
WHERE T1.U_NAME = [%0]
```

**用途**：`WTM1` 記的是範本的「發起人」，也就是這個人送出單據時會被哪些範本攔下來。人員異動時，除了他負責核准的階段（查詢 2），也要看他是不是某些範本的發起人。

## 【What For】常見情境與應對

### 情境一：核准卡住，不知道誰有權核准

先在 B1 開「管理 → 核准程序 → 核准狀態報表」，找到那張單據，看它套用的範本和目前停在哪個階段。

再用查詢 1 以那個階段代碼篩選，就知道現在是誰該核准，直接聯絡對方。

### 情境二：主管異動，需要更新核准設定

執行查詢 2，輸入舊主管姓名，列出他負責的所有核准階段，逐一進入設定頁面替換核准人員。

### 情境三：系統整理，盤點所有現行核准架構

執行查詢 1，匯出結果給客戶的 IT 或管理部門確認，作為定期審查的依據。

---

## 常見陷阱

**陷阱一：修改核准階段後，舊的待核准單據不受影響**

已進入待核准狀態的單據，不會因為你更新了核准階段的人員就自動轉給新的核准者。

要嘛請原本階段的核准人處理掉，要嘛請發起人取消那張草稿重新送單，讓它套用新的設定。

**陷阱二：同一個人在多個階段出現**

一個使用者可能同時是多個核准階段的核准人，查詢 2 會把全部列出來，不要只改其中一個。

**陷阱三：核准範本的啟用條件未同步更新**

核准範本裡除了階段，還有觸發條件（如金額門檻、特定使用者）。更換核准人員時，順便確認觸發條件是否還符合現行制度。

---

## 實作提醒

- 每次客戶有人員異動，主動執行查詢 2 確認影響範圍，不要等單據卡住才處理
- 將查詢 1 的結果納入導入文件的「核准架構表」，定期更新
- 建議客戶建立「核准架構審查」的年度 SOP，由顧問或 IT 定期執行這幾支 SQL 並回報給管理層
