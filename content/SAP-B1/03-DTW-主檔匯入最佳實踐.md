# DTW 資料傳輸工作台：主檔匯入最佳實踐

## 前言

Data Transfer Workbench（DTW）是 SAP Business One 顧問在導入專案中使用頻率最高的工具之一。它讓顧問能夠將客戶現有系統的資料（通常是 Excel 或 CSV 格式）批次匯入 SAP B1，省去手動逐筆建立的時間。然而，DTW 的使用門檻並不低：欄位定義、資料型別、匯入順序、錯誤處理——每一個環節都可能導致批次匯入失敗。

對資深顧問來說，DTW 不只是「匯入工具」，更是**資料品質的照妖鏡**。資料能不能順利匯入，往往反映了客戶原有資料的整理程度。掌握 DTW 的最佳實踐，意味著同時掌握了如何引導客戶整理和驗證資料。

---

## 一、DTW 核心功能概覽

DTW 的核心設計概念是：透過標準化的 CSV/Excel 範本，將資料對應到 SAP B1 的物件結構，再呼叫 DI API（Data Interface API）執行實際的資料寫入。

這個架構有兩個重要意涵：

1. **DTW 寫入的資料，等同於透過 DI API 操作的資料**，會觸發 SAP B1 的所有業務邏輯驗證（包含科目決定、稅別對應、控制科目檢查等）。這是為什麼 DTW 的報錯訊息有時會和系統畫面上的報錯完全相同。

2. **DTW 本身不做資料轉換**，它只是資料的搬運工。資料整理、格式轉換、欄位對應——這些工作都必須在匯入前完成。

### 物件類型

DTW 將資料分為三種類型：

| 類型 | 說明 | 常見物件 |
|------|------|----------|
| Master Data | 主檔資料，可重複更新 | OCRD（業務夥伴）、OITM（品項）、OHEM（員工） |
| Setup Data | 設定資料 | OUSR（使用者）、OWHS（倉庫）、OUDP（部門） |
| Transactional Data | 交易資料，匯入後無法直接修改 | OJDT（日記帳）、OPDN（收貨採購單） |

## 二、主檔匯入順序與欄位重點

### 業務夥伴主檔（OCRD）

業務夥伴是整個 SAP B1 交易流程的核心，必須優先匯入。

必填欄位：
- `CardCode`：唯一識別碼，一旦匯入後無法修改，命名規則需事先與客戶確認。
- `CardName`：顯示名稱。
- `CardType`：C（客戶）/ S（供應商）/ L（潛在客戶）。
- `Currency`：預設交易幣別。
- `LicTradNum`：統一編號（台灣環境需填入）。

若業務夥伴有銀行帳號資料，需搭配 **OCRB（BPBankAccounts）** 一起匯入：
- `BPCode`：對應 OCRD 的 CardCode。
- `AccountNo`：銀行帳號。
- `BankCode`：需事先在系統中建立對應的銀行代碼。

### 品項主檔（OITM）

品項主檔的複雜度在於與其他設定的相依關係：
- 品項群組（OITB）、倉庫（OWHS）必須在 OITM 前建立完成。
- 若品項有批號管理需求，`ManBtchNum` 欄位必須設為 `Y`，且此設定會直接影響期初庫存帳的匯入格式。

### 會計科目表（OACT）

OACT 是所有財務相關設定的基礎，欄位設定有較高的技術要求：

| 欄位 | 說明 | 設定通則 |
|------|------|----------|
| `Postable` | 是否可過帳 | 最底層科目設 `Y`，其餘設 `N` |
| `ActType` | 科目類型 | N（資產負債）/ I（收入）/ E（支出） |
| `LocManTran` | 控制科目 | 應收、應付最底層設 `Y`，其餘一律 `N` |
| `Finanse` | 現金科目 | 需認列為現金的科目設 `Y` |

資料格式注意：`AcctCode` 和 `FatherNum` 的資料格式（數字或文字）必須一致，否則 DTW 會無法識別階層關係。

### 員工主檔（OHEM）

員工主檔有 `empID` 欄位為自動遞增（Auto Increment），匯入時通常留空或填 0，由系統自動產生。匯入前需先建立：
- 部門主檔（OUDP）
- 職稱主檔（OHPS）

## 三、建立客製化匯入範本

DTW 提供的預設範本包含物件的所有欄位，對於大多數匯入情境而言，欄位數量過多，反而容易造成混淆。建議建立只含必要欄位的客製化範本：

1. 在 DTW 中選擇「建立客製化範本」（Create Template）。

2. 選擇目標物件（Object），移除不需要的欄位。

3. DTW 會匯出 `.xlt` 格式的範本檔案。

**實務技巧**：DTW 的欄位刪除介面只能逐一刪除，效率較低。建議改用另一種方式：先匯出完整的範本，再在 Excel 中直接刪除不需要的欄位列，然後儲存為 CSV 進行匯入。這樣更有彈性，也方便留存為未來專案的參考範本。

## 四、常見錯誤排除

### 錯誤一：There is no company database in the server

這是在非伺服器主機上執行 DTW 時最常見的錯誤。原因是 DTW 透過 DI API 連線，而 DI API 的 `b1-local-machine.xml` 設定檔中的 SLDAddress 與實際 SLD 位址不一致。

排除步驟：
1. 確認 DI API 是否已安裝（32-bit 版本）。
2. 確認 hosts 檔案（`C:\Windows\System32\drivers\etc\hosts`）中，伺服器主機名稱能正確對應 IP 位址。
3. 複製 SAP B1 Client 資料夾（`C:\Program Files\SAP\SAP Business One\Conf\b1-local-machine.xml`）到 DI API 的同名設定檔位置（`C:\Program Files\SAP\SAP Business One DI API\Conf\`）。

### 錯誤二：元素區域名稱不可為 NULL 或空字串

（The local name for elements or attributes cannot be null or an empty string）

這個錯誤通常表示 CSV 資料中有異常字元或空欄位導致 XML 解析失敗。常見原因：
- 欄位名稱列（第一列）有空白欄位標題。
- 資料中含有特殊字元（全形空格、換行符號）。
- 檔案編碼不正確：建議使用 UTF-8（with BOM）或 Unicode。

### 錯誤三：資料匯入部分成功、部分失敗

DTW 每一筆資料都是獨立執行，部分失敗不會回滾已成功的資料。處理方式：
- 查看 DTW 的 Error Log，找出失敗筆數與原因。
- 修正失敗的資料列後，只重新匯入失敗的部分。
- **不要整批重新匯入**，已成功的資料會產生重複。

## 五、小批量測試策略

正式匯入前，小批量測試（Pilot Import）是降低風險最有效的方法。

**建議做法**：
1. 從完整資料中取出 5-10 筆具代表性的資料（含邊界案例，如：有多個聯絡人的業務夥伴、含批號的品項）。
2. 在測試資料庫執行匯入，確認所有欄位正確對應。
3. 在系統畫面中逐筆確認匯入結果，特別注意自動產生的值（如科目決定、稅別）。
4. 測試無誤後，再執行全量匯入。

## 常見陷阱

**陷阱一：用 Excel 開啟 CSV 後直接儲存**
Excel 在開啟 CSV 後儲存，可能自動改變數字格式（如前導零被去除、科目代碼被轉成數值），造成匯入後資料與預期不符。建議用文字編輯器（如 Notepad++）做最終儲存，並確認編碼設定。

**陷阱二：在正式資料庫測試**
任何 DTW 匯入都應先在測試資料庫執行。交易資料（Transactional Data）一旦匯入就無法直接刪除，錯誤的開帳資料必須透過沖銷分錄才能處理，代價高昂。

**陷阱三：忽略日誌（Log）檔案**
DTW 的 Log 檔案記錄了每一筆資料的處理結果。許多顧問只看「匯入完成」的彈跳訊息，沒有仔細看 Log，結果發現部分資料靜默失敗了。每次匯入後，務必開啟 Log 確認成功筆數是否等於預期筆數。

## 顧問建議

DTW 的核心價值是提高資料匯入效率，但前提是資料本身已經整理好。在實務專案中，資料整理的時間往往遠超過實際匯入操作的時間。建議在專案計畫中，為「資料清理與對齊」安排足夠的時間，並讓客戶的 Key User 參與這個過程，因為只有客戶自己才知道哪些資料是有效的、哪些是歷史廢料。

建立一份屬於自己的 DTW 範本庫（涵蓋常用物件的欄位說明與資料範例），是資深顧問效率的重要來源。每個新專案都可以從這份範本庫出發，大幅縮短準備時間。
